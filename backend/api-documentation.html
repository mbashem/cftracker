Backend developer reference

REST API documentation

GitHub sign-in, Codeforces ownership verification, and private problem lists. This reference describes the current Go backend; examples are illustrative, not recorded live responses.

Open the API testing workspace → to send requests, sign in with GitHub, or use a saved bearer token.

Application base: http://localhost:8080/api/v1. Replace the origin with your deployment host. Health probes use /health directly.

Send JSON bodies with Content-Type: application/json. Protected routes require a bearer token. JSON response fields use snake_case; timestamps are RFC 3339 strings, with optional fractional seconds and timezone offsets.

The frontend setting VITE_BACKEND_API_URL should end at /api; the frontend appends /v1. Unversioned application routes and / are not registered.

Authentication

  1. Navigate the browser to the backend's GitHub login endpoint.
  2. The backend sets an HTTP-only state cookie and redirects to GitHub.
  3. GitHub redirects directly to the allowlisted calling origin plus /callback/auth-gh. Register this URL in the GitHub OAuth app as well.
  4. The frontend forwards the returned code and state to the backend callback, including cookies.
  5. Use the returned token in Authorization: Bearer <token> for protected requests.

Session JWTs expire two hours after issuance. The API has no refresh, logout, or token-revocation endpoint. Client logout clears local credentials and private state; it does not revoke an issued JWT.

The OAuth state cookie is named cftracker_github_oauth_state, has a ten-minute maximum age, and is consumed before the code exchange. It is HTTP-only, scoped to /, and uses Secure; SameSite=None for HTTPS, otherwise SameSite=Lax. A new login replaces the pending challenge.

Browser clients must include credentials on the callback, for example credentials: "include". Their origin must be listed in CORS_ALLOWED_ORIGINS. Behind HTTPS termination, forward X-Forwarded-Proto: https so the backend sets the secure cookie correctly.

Example protected request

API_ORIGIN='http://localhost:8080'
API_BASE="$API_ORIGIN/api/v1"
JWT='REPLACE_WITH_SESSION_TOKEN'

curl "$API_BASE/user/profile" \
  -H "Authorization: Bearer $JWT"

  "avatar_url": "https://example.test/avatar.png",

ListItem

{
  "list_id": 5,

Codeforces ownership is verified when cf_handle is nonempty and equals cf_verified_handle, ignoring case. There is no separate verification boolean. A stored verified handle can differ from the selected handle.

Health

GET /health/live

Public · no request body

Checks whether the HTTP process can respond. No database or provider call.

HTTP 200
{"status":"alive"}

Response header: Cache-Control: no-store.

GET /health/ready

Public · no request body

Pings the shared database pool with a one-second deadline, including pool waits and any earlier request cancellation.

HTTP 200
{"status":"ready"}

HTTP 503
{"status":"unavailable"}

Response header: Cache-Control: no-store. This checks connectivity, not migration state or GitHub/Codeforces availability. Health probes are exempt from application rate limits.

GitHub OAuth

GET /api/v1/auth/github/login

Public · browser navigation · no request body

Uses the request's Origin, or the Referer origin when absent, and requires an exact match in CORS_ALLOWED_ORIGINS. GitHub returns directly to that origin plus /callback/auth-gh. No redirect environment variable or alternate-domain parameter is supported. Sets the existing HTTP-only OAuth state cookie and redirects to GitHub with user:email scope.

HTTP 307
Location: [GitHub authorization URL]
Set-Cookie: cftracker_github_oauth_state=[challenge]; ...

Errors: 400 — Invalid frontend origin; 500 — Failed to initialize GitHub login; 429 — authentication IP allowance exhausted.

GET /api/v1/auth/github/callback

Public route · requires the matching OAuth state cookie

Query parameters: code (GitHub authorization code) and state (the value GitHub returned). No JSON body. The state must match the cookie from login.

After validating state, the backend exchanges the code, retrieves the GitHub user, creates or updates the local account, and signs a session JWT. The response is JSON; it does not redirect to the frontend.

HTTP 200
{
  "user": {
    "id": 7,
    "github_id": 42,
    "github_username": "example-user",
    "email": "user@example.test",
    "avatar_url": "https://example.test/avatar.png",
    "cf_handle": "",
    "cf_verified_handle": "",
    "admin": false
  },
  "token": "SESSION_JWT"
}

Errors: 400 — Invalid GitHub OAuth state; 502 — GitHub user request failed; 500 — token exchange, user retrieval/decoding, local persistence, or JWT generation failed; 429 — callback IP allowance exhausted.

Once a valid state is consumed, a failed exchange requires starting a fresh login. Missing or invalid code is handled by the provider exchange and is not a separate local 400 validation.

Profile & Codeforces ownership

All four endpoints require bearer authentication. They may return 404 {"error":"User not found"} or 500 {"error":"Failed to load user"} when loading the account.

GET /api/v1/user/profile

Bearer token · no request body

Returns 200 {"user": User}. Use this endpoint after updating or verifying a handle to refresh the client profile. No session token is included.

PUT /api/v1/user/cfhandle

Bearer token · JSON body 
{"cf_handle":"tourist"}

cf_handle is required, has a binding limit of 255 characters, and is trimmed. Whitespace-only values and semicolons are rejected.

Without a stored verified handle, this only selects a handle: it does not contact Codeforces or prove account existence. When changing a previously verified handle, the backend resolves its history through Codeforces. A matching rename updates both handles and preserves verification. Selecting a different account retains the old proof but leaves the selected account unverified.

HTTP 200
{"message":"CF Handle updated"}

Errors: 400 — Invalid request; 409 — Codeforces handle changed; please retry; 500 — Failed to update CF Handle; Codeforces provider errors; 429 when a required provider lookup is on cooldown.

A failed historical lookup leaves stored handles unchanged. Re-read the profile before retrying a stale update.

GET /api/v1/user/cfverification-token

Bearer token · no request body or query parameters

Creates or reuses a nine-character challenge bound to the authenticated user and selected handle. Pending challenges expire after one hour and are stored in memory; restarting the backend loses them.

HTTP 200
{"token":"aB3dE6gH9"}

Errors: 400 — User is already verified; 500 — Failed to generate token.

Select a handle first. The current handler does not explicitly reject an empty selected handle. This challenge is distinct from the session JWT and is not an Authorization credential.

GET /api/v1/user/verify-cftoken

Bearer token · no request body or query parameters · updates ownership state
  1. Select your Codeforces handle with PUT /user/cfhandle.
  2. Obtain the ownership challenge.
  3. Set that Codeforces account's first name to the exact challenge and save its profile.
  4. Call this endpoint. The backend reads Codeforces user.info and compares firstName with its stored challenge.
  5. On success, refresh your profile. The challenge is deleted and cf_verified_handle is set to the selected handle.
HTTP 200
{"message":"User verified"}

The challenge is read server-side; do not submit it as a query parameter. Handle matching ignores case, while the challenge comparison is exact. The provider lookup disables historical-handle matching for this ownership check.

Errors: 400 — User is already verified or Invalid token (including missing, expired, or mismatched challenges); 409 — Codeforces handle changed; please retry; 500 — Failed to verify user. Please try again later!; provider errors; 429 on cooldown.

Private lists & items

Every endpoint requires bearer authentication. Ownership comes from the JWT; do not send user_id. A missing list and a list owned by another account both return 404 {"error":"List does not exist"}.

List names are trimmed, must contain 1–100 Unicode characters, and must be unique per account. Limits: 20 lists per account and 1,000 items per list. There is no pagination or exposed reorder endpoint.

GET /api/v1/lists

Bearer token · no request body

Returns owned lists ordered by ID. An account with no lists receives "lists": [].

HTTP 200
{
  "message":"Lists fetched successfully",
  "lists":[{"id":5,"user_id":7,"name":"Practice","created_at":"2026-10-26T12:00:00Z"}]
}

Database failure: 500 — Failed to find the list.

POST /api/v1/lists

Bearer token · JSON body 
{"name":"Practice"}
HTTP 201
{
  "message":"List created",
  "list":{"id":5,"user_id":7,"name":"Practice","created_at":"2026-10-26T12:00:00Z"}
}

Errors: 400 — Invalid format for malformed or invalid input; 409 — maximum of 20 lists per account reached; 500 — Failed to create list, including a duplicate name under the current error mapping.

Example request

curl -X POST "$API_BASE/lists" \
  -H "Authorization: Bearer $JWT" \
  -H 'Content-Type: application/json' \
  --data '{"name":"Practice"}'

GET /api/v1/lists/:listId

Bearer token · path parameter: list ID

Returns the list and its items as sibling fields. Items are ordered by position, creation time, then problem ID. An empty list returns "items": [].

HTTP 200
{
  "message":"List fetched successfully",
  "list":{"id":5,"user_id":7,"name":"Practice","created_at":"2026-10-26T12:00:00Z"},
  "items":[{"list_id":5,"problem_id":"1900A","position":0,"created_at":"2026-10-26T12:01:00Z"}]
}

Database failures: 500 — Failed to find the list or Failed to get list items.

PUT /api/v1/lists/:listId

Bearer token · JSON body 
{"name":"Updated practice"}
HTTP 200
{"message":"List name updated"}

The same name-validation rules apply. The response does not include the updated list; refetch it if needed. 400 — Invalid format; 500 — Failed to update list, including duplicate-name database failures.

DELETE /api/v1/lists/:listId

Bearer token · no request body

Deletes the owned list and its items through database cascade. A second delete of the now-missing list returns 404.

HTTP 200
{"message":"List deleted"}

Database failure: 500 — Failed to delete list.

PUT /api/v1/lists/:listId/item

Bearer token · JSON body 
{"problem_id":"1900A","position":0}

problem_id is required, trimmed, and limited to 100 characters before trimming. position must be explicitly supplied as an integer greater than or equal to zero; zero is valid. The API does not validate the problem against Codeforces. Positions need not be consecutive or unique.

HTTP 201
{
  "message":"Successfully added item to list",
  "item":{"list_id":5,"problem_id":"1900A","position":0,"created_at":"2026-10-26T12:01:00Z"}
}
Despite the PUT method, this endpoint inserts an item; it does not update or upsert an existing item. Duplicate problem IDs in the same list currently produce a database error mapped to 500. Do not blindly retry an uncertain insertion: read the list first.

Errors: 400 — Invalid format; 409 — maximum of 1000 items per list reached; 500 — Failed to add item to list. At quota, even an attempted duplicate may return 409 because the count is checked first.

Example request

curl -X PUT "$API_BASE/lists/5/item" \
  -H "Authorization: Bearer $JWT" \
  -H 'Content-Type: application/json' \
  --data '{"problem_id":"1900A","position":0}'

DELETE /api/v1/lists/:listId/item/:itemId

Bearer token · no request body

itemId is the problem ID string, such as 1900A, not a numeric row ID. URL-encode it as a path segment. Removing an absent item still succeeds when the caller owns the list.

HTTP 200
{"message":"Item deleted from list"}

Database failure: 500 — Failed to delete item from list.

All list-specific routes reject nonnumeric or overflowing listId values with 400 {"error":"Invalid list Id"}. Numeric IDs that do not identify an owned list return 404.

Errors & limits

Application errors use a single string field, without a machine-readable error code:

{"error":"Unauthorized"}

Handle status codes explicitly. Unregistered routes, CORS rejection, and infrastructure failures may return a different body or no JSON; do not assume every failure has an error field.

Common responses; endpoint sections describe operation-specific errors.
StatusMeaningClient action
400Invalid input, malformed list ID, invalid OAuth state or ownership challengeCorrect input; restart OAuth or obtain a new challenge when appropriate.
401Missing, malformed, invalid, or expired bearer token: UnauthorizedClear the invalid session and private state; sign in again.
403A browser origin may be rejected by CORS middleware.Check deployment origin configuration; this need not be JSON.
404User/list missing, list not owned, or route unregisteredStop using stale resources; verify the versioned path.
409List/item quota or concurrent Codeforces handle changeFree capacity or refresh the profile before retrying.
413Request body exceeds 16 KiBReduce the full body size, including trailing whitespace.
429Too many requests. Try again later.Respect the integer seconds in Retry-After.
500Database, token-generation, or some provider failuresShow the failure; check current state before retrying a write.
502Rejected or malformed upstream responseReport provider failure and allow a later retry.
503Readiness check failedWait for database connectivity; do not interpret this as schema verification.

All request bodies are capped at 16 KiB before decoding. Failure to read a body returns 400 {"error":"Failed to read request body"}. Handler validation rejects malformed and missing required fields; unknown JSON fields are not a documented strict-schema guarantee.
