# Frontend Tests

Apply [develop-frontend](../develop-frontend/SKILL.md) alongside this skill for frontend execution boundaries and the repository Node version. Keep work scoped to the requested behavior: a test-plan request produces a plan rather than executable coverage for the entire application.

## Repository setup

- Read `package.json`, `.nvmrc`, and `vite.config.mts` before selecting commands or changing test configuration. The current suite uses Vitest with jsdom and discovers `tests/**/*.test.{ts,tsx}`.
- Place pure-function tests in `.test.ts` and JSX tests in `.test.tsx`, under the corresponding feature folder in `tests/`. Follow nearby examples rather than introducing another framework or global setup for a local need.
- Import APIs explicitly from `vitest` and React Testing Library. Use ordinary Vitest assertions; do not assume jest-dom matchers, user-event, or a browser runner are installed.

## Codex disclaimer

For every new or substantially rewritten test generated by Codex, put this comment immediately above its `test` or `it` declaration:

```ts
// Generated by Codex and not thoroughly checked for correctness.
```

For parameterized tests, place it above the `test.each` or `it.each` declaration so it applies to every generated case. A file header may supplement but does not replace the per-test comment. Do not relabel untouched existing cases or remove the disclaimer merely because automated checks pass. In written test plans, include the same disclaimer within every case so it remains attached when copied elsewhere.

## Assertions and fixtures

- Assert observable behavior: visible content, accessible state, destination URL parameters, returned calculations, or persisted values. Do not reproduce the production algorithm to calculate expected results.
- Name cases after the scenario and outcome. Prefer explicit expected values from small fixtures; introduce shared fixture helpers only for meaningful repetition. Pass scenario data into setup helpers and do not mutate shared defaults.
- Select controls by role and accessible name where possible. Use test IDs for probes or content with no useful accessible selector, such as router location probes.
- Keep the subject under test real. Mock network, authentication, or unrelated dependencies at a narrow boundary; use the term `mock` for test doubles. Use real state transitions when behavior spans multiple actions.
- Search existing test support and suites before adding a mock. Reuse existing mocks; do not create duplicate mocks for the same dependency. Extend the shared mock with scenario-specific data, responses, or errors when needed. If a reusable mock exists only inside another suite, extract it into shared test support and update affected callers instead of copying it.
- Give shared mocks a common initializer and reset their state explicitly for each test so reuse does not introduce test-order dependencies. Consolidate duplicate mocks encountered in the touched test scope without expanding into unrelated suites.
- For regressions, identify the failure the assertion would catch. Avoid tests for trivial reversible edits and assertions that merely restate implementation structure.
- Preserve `undefined` for absent application values; use `null` where a platform or persisted-data contract requires it.

## Components, hooks, and state

- Use `render` for component behavior and `renderHook` for hook contracts. Wrap navigation subjects in `MemoryRouter`; include the actual Redux provider/store when store behavior is part of the test.
- Use React `act` for direct hook state updates and timer advancement. Await observable asynchronous results rather than arbitrary sleeps.
- Register Testing Library `cleanup` in teardown, as existing suites do. Reset relevant localStorage, mock state, and clock state explicitly. Restore spies and real timers after cases that change them.
- For delayed storage writes, use fake timers to check the latest eligible write and cancellation on unmount, key changes, or disabled persistence. Avoid coupling unrelated tests to the current delay.
- For URL state, inspect parameters with `URLSearchParams` instead of asserting query-string order. Cover precedence, invalid values, clearing optional values, Back/Forward, and preservation of unrelated keys when relevant to the requested change.
- For saved versus temporary filters, verify displayed state and persisted preferences. Temporary `useFilterStorage=false` navigation must not overwrite saved problem filters.
- For asynchronous requests, cover failure and superseded responses when relevant; stale responses must not replace current-user state. Keep unit tests independent of live Codeforces, GitHub, backend, analytics, and Utterances services.
- Freeze time for date calculations and document timezone assumptions. Check inclusive/exclusive boundaries and distinguish submission counts from distinct problem counts using hand-calculated fixture totals.

## Test plans

Consult `docs/frontend-test-plan.md` as a coverage inventory when relevant, not as an unquestioned requirements source. Include an ID, priority, preconditions, steps, expected result, and disclaimer in each proposed case. Mark cases unexecuted until run; distinguish intended acceptance criteria from observed behavior and unresolved product decisions.

## Validation and reporting

Use the exact Node version in `.nvmrc`, through NVM if necessary. Run the smallest relevant suite first, for example:

```sh
npm run test:frontend -- tests/home/homeStatistics.test.ts
```

For executable test changes, run the full frontend suite and checks required by the change or repository conventions. `npm run verify:frontend` runs tests, typecheck, lint, and build. Repeat or broaden passing checks only for new changes or unresolved concerns. Documentation-only plans do not require a frontend build.

Do not start, open, or interact with a running application unless the user explicitly requests real-app execution in the current task, as required by develop-frontend. jsdom tests do not establish browser layout, focus, OAuth, or real-service correctness. Report what ran, results, and outstanding browser/integration checks without implying they passed.
