# UI testing plan

Prepared against commit `992a6993` on 2026-10-05. Scope: the main CFTracker frontend; backend and manage-contests require separate plans.

This document proposes acceptance checks. Every case is **Unexecuted**; static inspection and existing jsdom tests do not establish a browser pass. Expected results below are intended acceptance criteria, not observations. Product decisions explicitly marked **Decision required** must be resolved before assigning a pass or fail to that part of a case.

## Execution setup

- UI testing is excluded from CI. Run these browser cases on demand as a separate workflow because of their execution time. Any future UI automation must use a separate command and must not be added to CI, `verify:ci`, `verify:frontend`, or commit/push hooks. Existing non-browser checks keep their current execution policy.
- Record the deployment URL, exact tested commit/build, browser/version, viewport, timezone, theme, backend/debug flags, and session state with each run. Use Node `22.22.0` when preparing this repository.
- Use a disposable browser profile and disposable backend accounts/lists. Keep production accounts and lists out of mutation cases. Run controlled-response cases on a test deployment; isolate actual service checks in UI-047 and UI-048.
- Start with Chrome desktop at 1440 × 900 and Asia/Dhaka. Repeat the responsive and keyboard cases in Firefox and Safari, at 320 × 568, 375 × 812, and 768 × 1024, in both themes and at 200% zoom. These are proposed test dimensions, not a declaration of browser support.
- Reset storage, cookies, URL parameters, and network overrides between independent cases. For persistence cases, retain only the state explicitly named in the preconditions. Await visible completion or a recorded request outcome; do not use arbitrary sleeps as proof of completion.
- Reuse `tests/support/problemFixtures.ts`, `contestFixtures.ts`, `statisticsFixtures.ts`, and `submissionFixtures.ts` where their scenarios fit. Reuse/extend `frontendMocks.ts`, `backendMocks.tsx`, `router.tsx`, `analyticsMocks.ts`, and `spinnerMocks.ts` for corresponding automated checks. Do not copy mocks into a new suite. Browser acceptance checks must render real controls, Chart.js canvases, SVG charts, routing, and application state; the existing `chartMocks.ts` renderer substitutes cannot prove chart appearance.
- The repository currently has Vitest/jsdom tests and no configured browser test runner. This plan does not install a framework or authorize starting/interacting with an application. Browser execution is a later task requiring an explicit request under the frontend development skill.

### Controlled data and independent expected totals

Use a small isolated catalog containing four Div. 2 problems: A (rating 800), B (1000), C (1200), D (unrated), with distinct IDs and searchable names. Add another category and an unclassified contest for category filtering; specify their expected matching IDs in the run record. Include shared contest equivalents in a separate scenario rather than silently changing these totals.

For statistics, use five raw submissions from one handle: two accepted submissions to A and one rejected submission to B on 2026-10-04; one acceptance to C and one rejection to D on 2026-10-05. Set their times away from midnight in Asia/Dhaka. Freeze the test clock at 2026-10-05 12:00 Asia/Dhaka where supported.

The independent oracle is **5 submissions**, **3 accepted / 2 rejected (60% accepted)**, **2 distinct solved problems (A, C)**, **2 distinct attempted problems (B, D)**, **2 active days**, and **1000 average solved rating**. The Div. 2 category chart has Solved = 3 and Attempted = 2, with no Unsolved slice. Heatmap day values are 3 and 2. Use actual supported rejected verdicts in the fixture and record their labels. Do not calculate expected results by calling the implementation under test.

## Priorities and recording

**P0:** core access, correct results, account isolation, and mutation integrity. **P1:** filtering, recovery, persistence, accessibility, responsive and chart behavior. **P2:** broader visual/performance investigation and secondary integrations.

Each row is one case. For parameterized checks, record an outcome for each browser, theme, data variant, or response variant rather than treating one run as evidence for all variants. Capture actual result, screenshot where useful, URL, request/status evidence, and issue reference. Screenshots alone do not establish numerical correctness. Use Passed, Failed, Blocked, or Unexecuted; there are no expected-failure cases.

## Execution order and exit criteria

1. Run P0 startup/navigation, controlled numerical checks, authentication/list integrity, and stale-response cases on the primary browser.
2. Run P1 URL/persistence/error recovery, real-chart, keyboard and responsive cases; then repeat the matrix for browser-specific controls and rendering.
3. Run isolated real-service integration cases, followed by performance/visual investigations with agreed baselines and budgets.

For an agreed release scope, all applicable P0 cases must pass with evidence; outstanding P1 defects need explicit triage; blocked decisions and omitted variants remain listed. Do not claim complete UI coverage from a code coverage percentage. Existing Vitest checks are regression evidence and should accompany browser verification when executable code changes, but this documentation-only task does not require rerunning the suite.

Suggested execution record: `ID | build | browser/version | viewport | timezone | theme | account/data variant | actual result | status | evidence/issue`. Keep credentials and bearer tokens out of screenshots and logs.
