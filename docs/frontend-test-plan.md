# Frontend test plan

Status: Draft generated by Codex. Automated coverage for Problems and Navigation, startup, and menu was added and run on 2026-10-03; complete manual cases remain unexecuted. Based on static inspection of the repository on 2026-10-03.

Scope: The main CFTracker React frontend in `src/`, its routes, state/hooks, shared controls, browser storage, and frontend interactions with Codeforces, the backend, GitHub OAuth, Utterances, and analytics. `manage-contests` is a separate application and is outside this plan; backend internals are outside scope.

Every case carries its own disclaimer so it remains attached when copied into a tracker. Expected results are draft acceptance criteria, not proof of current behavior. Cases labeled “proposed acceptance,” “record,” or “review” need a human decision before they become release gates; known implementation behavior may differ.

## Execution setup

- Use a test deployment and disposable authenticated account/lists. Mock external responses for repeatable failure, timing, OAuth, and authorization checks; use a small integration smoke pass for real service contracts.
- Run with backend availability enabled and disabled, clean and populated storage, anonymous and authenticated sessions, both themes, and the browser/viewport matrix below. Repeat applicable cases across these variants rather than only the default configuration.
- Freeze the clock for date cases. Use Asia/Dhaka as the primary timezone and a DST-observing timezone for boundary checks. Encode timestamps in seconds as required by the application.
- P0 = core flow or integrity check; P1 = regression/edge coverage; P2 = exploratory polish. Execute P0 first, then P1, then P2.
- Each row provides the action sequence and expected result. Unless overridden, start with loaded fixtures, clean storage, anonymous access, and a non-random route. List cases require backend-enabled authentication and disposable lists; persistence cases require explicitly seeded storage; failure cases require mocked failures.
- For each execution record case ID, build/commit, environment, browser, viewport, theme, timezone, fixtures, actual result, Pass/Fail/Blocked/Not run, evidence, and defect link. All cases initially have status **Not run**.
- This task does not authorize starting or interacting with the application under the develop-frontend skill. The plan describes future browser checks; no browser checks were performed while preparing it.

## Shared fixtures and independent oracles

F1: Five submissions over two distinct local dates inside the selected Custom period: rated problem A (800) has one WRONG_ANSWER and two OK submissions; unrated problem B has one OK; rated problem C (1200) has one WRONG_ANSWER. Expected distinct totals: 2 solved, 1 attempted unsolved, 2 active days, average solved rating 800. Verdict totals: OK = 3, WRONG_ANSWER = 2. Add untouched problem D (1600) to the catalog for unsolved filters. Use legal fixture objects with contest IDs, indexes, participant types, and timestamps, and keep submission input ordered where the consumer requires it.

F2: A catalog containing different contest categories, participant types, tags, rating boundaries, unrated entries, shared-contest mappings, one zero-problem contest, and enough rows for three pages. Add entries at exact range boundaries and a supported high contest ID. Calculate expected memberships by hand from the fixture rather than reusing the application's filter functions.

F3: A disposable user with two lists, one empty list, ordered items, and mocked success/validation/401/403/404/500 responses. Use a second account or mocks for foreign-list access. Never delete real user lists for testing.

## Completion criteria

Before adopting this plan, a reviewer checks each expected result against agreed requirements, especially tag matching, invalid/reversed ranges, unknown routes, missing OAuth parameters, expired sessions, list deep links, mutation modal behavior, and accessibility. Execute all applicable P0/P1 cases, document excluded variants, resolve blocking defects, and record the remaining risks. A clean `npm run verify:frontend` is necessary automated evidence, but does not replace execution of the browser and integration cases.
